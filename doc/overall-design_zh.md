# 总体设计

本文档定义 `dsh-memory-note` 的总体设计。它确定运行时结构、组件职责、存储边界、并发模型和记忆生命周期。具体的 JSON 请求、响应与错误契约由 `protocol-v1-proposal.md` 单独定义。

本项目保持本地化和轻量。它的核心职责是：安全的一次性执行、与路径无关的工作区身份、跨进程协调、显式的记忆状态迁移、乐观版本检查，以及严格的用户审批边界。

## 1. 运行时架构

```text
DeepSeek Harness / 未来的编码代理
                  |
        TypeScript 适配器
                  |
        一次性进程 + JSON
                  |
          Go 可执行文件
                  |
             SQLite 文件
```

Go 可执行文件采用一次性（one-shot）模式。每次进程调用只执行一个子命令：

```text
dsh-memory-note <subcommand> '<json request>'
```

因此，每个公开操作都有三个对应的接口：

1. 一个子命令名；
2. 一个由 Go 可执行文件处理的 RPC 函数；
3. 一份独立的 JSON 请求/响应契约。

每个业务命令都向 stdout 写入恰好一条协议响应。诊断信息写入 stderr。`version` 向 stdout 输出一行版本字符串并以 0 退出；`help` 向 stderr 输出用法说明并以 0 退出；二者都不输出 JSON response，也都不暴露为 Harness 工具。确切的命令与退出码契约由协议文档定义。

### 1.1 Session

每次一次性调用都会创建一个 `Session`，它是最高层级的运行时组件管理器。它不是持久化的 Harness 会话，也不代表长期记忆数据。

一个 Session 拥有该次调用所需的资源：

- 一个密码学随机的会话 ID；
- 解析后的 `DSH_MEMORY_NOTE_HOME` 路径；
- 一个私有临时目录；
- 用于所选子命令的 RPC 分发器；
- 该次调用打开的 SQLite 连接与事务；
- 以其会话 ID 获取的工作区读锁或写锁。

Session 的生命周期是固定的：

1. 解析进程参数，以选定子命令；
2. 创建会话 ID 和私有临时目录；
3. 解析并校验 `DSH_MEMORY_NOTE_HOME`；
4. 若 `DSH_MEMORY_NOTE_HOME` 不存在，则原子地初始化它；
5. 严格解码并校验 JSON 请求；
6. 获取所需的工作区锁；
7. 执行 RPC 函数并提交其 SQLite 事务；
8. 释放锁、关闭数据库并删除临时目录；
9. 发出一个响应并退出。

每条正常返回路径都会尝试清理。锁过期只是针对崩溃、被强制终止或清理失败时的兜底手段。

### 1.2 `main()` 与 RPC 分发

`main()` 是一个轻薄的进程入口点。它只负责创建 Session、选择一个子命令、委托给其 RPC 函数、序列化结果并决定退出码。

`main()` 中不得包含 SQL、记忆状态迁移、工作区迁移逻辑或重复的请求校验。每个子命令有一个命名清晰的处理函数和一个显式的请求/响应类型。只有在确有多个命令共享某行为时，才引入共享辅助函数。

无需任何守护进程、后台服务、网络监听器或常驻内存状态。

## 2. 存储布局

所有持久化数据库均使用 SQLite，扩展名为 `.db`。完整的 SQL schema、语句语义与存储不变式由 `sql-standard.md` 单独定义。存储布局如下：

```text
DSH_MEMORY_NOTE_HOME/
├── meta.db
└── memory/
    ├── workspace-{WID}-memory.db
    └── ...
```

默认的 `DSH_MEMORY_NOTE_HOME` 是 `~/.local/share/dsh-memory-note/`。它可被 `DSH_MEMORY_NOTE_HOME` 环境变量覆盖。配置的值必须解析为绝对路径。

工作区本身不存储任何插件数据库、WID 标记、锁文件或其他插件拥有的状态。因此，移动或删除工作区目录并不会隐式地移动或删除其记忆数据库。

在本文档的其余部分，**HOME** 指 `DSH_MEMORY_NOTE_HOME`，而非操作系统的 `$HOME` 目录。在代码中没有这个指代。

### 2.1 `meta.db`

`meta.db` 存储跨工作区共享的元数据：

- `workspace_id`，也称 WID，是由 SQLite 分配的非负整数；
- 工作区当前的规范化绝对路径；
- 工作区的创建时间、更新时间以及模式（schema）元数据；
- 每个 WID 的跨进程读/写锁记录。

`meta.db` 不存储记忆内容。它是把路径解析为 WID 的权威，并负责协调可能与工作区重绑定、清空或删除发生竞争的操作。

工作区名称不是身份。名称相同但绝对路径不同的目录可能拥有不同的 WID。WID 不是带前缀的字符串或随机令牌。记忆数据库文件名只取决于十进制表示的 WID，例如 `workspace-12-memory.db`。

WID 是稳定的，工作区删除后不会被复用。

### 2.2 工作区记忆数据库

每个工作区都有一个专属的 `workspace-{WID}-memory.db`。它只存储该工作区的记忆、状态、版本、元数据、来源、替换关系以及归档的历史版本。

任何查询或事务都不得合并来自不同工作区数据库的记忆行。决定打开哪个数据库文件的是来自 `meta.db` 的 WID，而不是请求中提供的文件路径。

SQLite 事务仍然负责记忆数据库内部的原子变更。`meta.db` 中的跨进程锁协调对数据库文件和工作区生命周期的访问；它并不能取代 SQLite 事务。

### 2.3 HOME 的初始化与完整性

每个 Session 在执行业务逻辑之前都会检查 HOME。

- 若 HOME 不存在，Session 会初始化一套完整的 `meta.db` 与 `memory/` 布局，然后继续执行。由于是初次（或者数据库没有相关数据，也认为是初次）涉及的工作区，无须经过用户同意。
- 若 HOME 存在，且包含一个常规文件 `meta.db` 和一个目录 `memory/`，Session 在完成模式校验后继续执行。
- 若 HOME 存在，但任一项目缺失、类型错误或不可信，Session 返回 `home_broken`。它绝不能静默地重建、截断或替换已有数据。

初始化完全在一个同级临时目录中完成，再通过一次原子重命名发布。并发的初始化进程可能竞争发布，但只要其中一个成功，其余进程就必须丢弃自己的临时布局并重新打开已发布的 HOME。

实现必须拒绝不安全的路径类型，例如可能将数据库或临时文件操作重定向到 HOME 之外的符号链接。临时名称必须派生自随机会话 ID，以私有权限创建，并且绝不包含原始的记忆内容。

## 3. 跨进程读/写锁

一次性模式允许多个 Go 进程并发运行。`meta.db` 提供按 WID 隔离的读/写锁。

所需的锁模式由操作决定：

| 操作 | 锁 |
|---|---|
| 记忆搜索或获取 | 读 |
| 记忆创建、更新、取代（supersede）、失效或删除 | 写 |
| 工作区重绑定、清空或删除 | 写 |
| 工作区注册 | 创建映射和数据库时的写协调 |

锁规则如下：

- 同一 WID 的多个读锁可以共存；
- 写锁与该 WID 的任何读锁或写锁互斥；
- 不同 WID 的操作互不阻塞；
- 重绑定、清空、删除或迁移工作区时，排除该 WID 的一切记忆访问；
- 锁的获取与冲突检查在一个简短的 `meta.db` 事务中原子完成；
- 每条锁记录包含其模式、持有者会话 ID、获取时间和过期时间；
- 持有锁的 Session 在正常完成时释放其锁；
- 过期的锁可以被回收，以免崩溃的进程永久阻塞工作区；
- 锁的获取有有界的等待时间，超时返回 `workspace_busy`。

如果某个操作的运行时间可能逼近其过期时间，其 Session 在仍是锁持有者时会续租。在开始一个修改事务之前，它必须核实自己仍持有写锁。如果锁的所有权已丢失，该操作必须中止，且不得开始新的写入。

这种租约设计协调正常运行中的进程，并从普通崩溃中恢复。它并不承诺能让一个被暂停超过完整租约期的进程安全恢复；那种更强的故障模型需要额外的隔离（fencing）机制，不在当前设计范围之内。

## 4. SQLite 与版本规则

记忆数据库事务为每个命令提供原子性：

- `memory-create`、`memory-update`、`memory-invalidate` 和 `memory-delete` 各自在一个事务内完成；
- `memory-supersede` 在一个事务内修改旧记录、创建新记录并建立两端的关联字段；
- `workspace-clear` 在一个事务内删除所有记忆行；
- `memory-search` 与 `memory-list` 在只读事务中运行，绝不修改数据；
- 只有在事务提交之后才发出成功响应。

所有 SQL 值都使用绑定参数。每个连接都启用外键约束。SQLite 的忙碌处理是有界的；它绝不能导致一次调用无限期等待。

每条记忆都有一个单调递增的 `version`。修改已有记忆必须提供 `expected_version`；比较与修改发生在同一个事务中。不匹配时返回 `version_conflict`，且不改变任何数据。

这是应用层上带类 MVCC 版本语义的乐观并发控制。它防止过时的 LLM 提案或并发的 Session 静默覆盖更新的事实。它并不承诺每个历史版本都可查询。

每次成功的 `memory-update`、`memory-supersede` 或 `memory-invalidate` 都会把被替换的记录归档为内部历史版本。`memory-delete` 删除当前记录及其全部归档版本；`workspace-clear` 在一个事务内删除全部记录与全部历史。历史版本是内部审计数据，绝不通过 JSON 协议暴露。

## 5. TypeScript 层职责

TypeScript 适配器目前专用于 DeepSeek Harness。它被刻意设计得很薄。

它负责：

- 注册 Harness 工具；
- 把每个工具调用映射为一个子命令和一份 JSON 请求；
- 传入该请求所需的当前工作区路径或 WID；
- 不经 shell 直接调用 Go 可执行文件；
- 解析单条 JSON 响应；
- 在调用任何写操作之前，使用 Harness 的用户审批机制。

它不实现存储、锁、事务、记忆状态迁移，也不维护请求语义的第二份拷贝。

LLM 可以不经用户审批直接调用读操作。它可以发现某条记忆与当前事实矛盾，并提议 `update`、`supersede` 或 `invalidate`，但它不能批准自己的提议。审批是 Harness 层的交互，而不是 LLM 可以自行设置的 JSON 布尔值。

Go 可执行文件机械地强制执行协议、状态、版本、事务和完整性规则。LLM 决定语义意图；用户授权实际效果。

## 6. 记忆模型与子命令

一条记忆不仅仅是一行内容。它包含身份、工作区归属、内容与元数据、来源信息、状态、版本、时间戳和替换关系。完整的字段级契约由 JSON 协议定义。

正常的状态迁移如下：

| 子命令 | 含义 | 结果 |
|---|---|---|
| `memory-create` | 记录一个新事实 | 带有新 ID 的新活跃记忆 |
| `memory-update` | 修订同一个事实 | ID 不变，版本递增 |
| `memory-supersede` | 用新事实替换旧事实 | 旧记录保留为已取代（superseded）；创建新的活跃 ID；建立替换关系 |
| `memory-invalidate` | 声明一个事实无效且无替代 | 记录保留为无效（invalid） |
| `memory-delete` | 显式删除一条记录 | 行从当前数据库中被物理删除 |

八个公开的记忆子命令如下：

### `memory-search`

按查询条件和过滤器检索候选记忆。过滤维度包括关键词、类型、范围和时间。它只是候选检索操作，而不是对某条记忆是否相关或属实的语义裁决。

### `memory-get`

按 `memory_id` 精确读取一条记忆，包括其完整内容、当前版本、来源、状态和替换关系。这是在提出版本敏感型写入之前使用的细粒度读取。

### `memory-list`

以游标分页列出某工作区任意状态的全部记忆，按 `updated_at`、`memory_id` 排序。返回不含 content、source、metadata 的紧凑行；`memory-get` 才是读取完整记录的细粒度接口。

### `memory-create`

创建一条全新的记忆并生成新的 `memory_id`。

### `memory-update`

修改同一事实的内容或元数据。`memory_id` 保持不变，版本递增。当新旧事实都应作为替换链可见时，不得使用本命令。

### `memory-supersede`

用新事实替换旧事实。新事实获得新的 `memory_id`；旧记录保留为 `superseded`；并以原子方式建立 `supersedes` / `superseded_by` 关系。

### `memory-invalidate`

当没有新事实替代某条记忆时，将其标记为无效。该记录仍然可供显式检索，并用于审计其不再活跃的原因。

### `memory-delete`

物理删除一条记忆行。它专用于明确的用户删除请求、误持久化或敏感信息清除。普通的事实过时使用 `supersede` 或 `invalidate`，而不是 `delete`。SQLite 的物理删除并不保证存储介质、文件系统快照或备份中的安全擦除。

## 7. 工作区身份与子命令

### `workspace-register`

为绝对工作区路径分配一个 WID，把映射记录到 `meta.db` 中，并原子地准备对应的记忆数据库。再次注册同一个规范化路径时返回已有的 WID，而不是创建第二个工作区。

### `workspace-resolve`

查询当前与某个规范化绝对路径关联的 WID 和元数据。它不会创建工作区或记忆数据库。

### `workspace-rebind`

在目录被移动或重命名之后，把已有的 WID 绑定到新的绝对路径。它只修改 `meta.db`；记忆数据库既不被移动也不被重命名，因为其文件名只取决于 WID。

重绑定是存储身份保持不变的工作区的常规迁移操作。新路径不得已属于另一个 WID。

### `workspace-clear`

保留工作区元数据、WID、路径绑定和数据库文件，但删除工作区数据库中的所有记忆。

### `workspace-delete`

删除工作区映射，并物理删除其记忆数据库和 SQLite 附属文件。该操作不会删除用户的工作区目录。被删除的 WID 不会被重新分配。数据损坏的工作区（只有元信息，没有记忆数据库）可通过此命令彻底清理。

## 8. 失败边界

响应信封和稳定的错误码由 JSON 协议定义。无论执行哪个命令，以下设计规则都适用：

- stdout 只包含协议响应；诊断信息使用 stderr；
- 命令在其事务或所需的文件系统操作完成之前，绝不报告成功；
- 格式错误或未知的 JSON 字段应被拒绝，而不是被忽略；
- 损坏的 HOME 或缺失的工作区数据库应被报告，而不是被静默替换为空数据库；唯一例外是 `workspace-delete`，它是清理记忆数据库缺失或损坏工作区的指定通道；
- 锁超时报告为 `workspace_busy`；
- 过期的记忆写入报告为 `version_conflict`；
- 无效的状态迁移被拒绝，且不修改记录；
- 临时文件在正常完成时被删除，并且除非某操作明确需要暂存字节，否则不含任何原始请求或记忆内容。

如果进程在发出有效响应之前就终止了，适配器将报告结果未知。它必须通过读操作检查当前状态，然后再提出另一次写入；绝不能盲目地通过修改 `expected_version` 来重试。

## 9. 设计原则

1. 一次进程调用执行一个明确的操作，并拥有一个短生命周期的 Session。
2. 工作区的身份是 WID；路径是可变的元数据。
3. 记忆数据库按 WID 隔离，并始终位于用户工作区之外。
4. 允许并发读；写和工作区生命周期操作按 WID 互斥。
5. SQLite 事务保障数据库原子性；`meta.db` 锁协调进程。
6. 版本检查防止过时写入，且无需存储完整的历史版本。
7. LLM 提出语义变更，用户批准写入，Go 强制执行机械安全。
8. 无效或模糊的状态被显式报告，而不是被静默修复。
9. JSON 协议是对外契约，`sql-standard.md` 钉死存储层语义，本设计文档解释各组件和规则存在的原因。

## 10. 版本与兼容性

对外只有一个版本：**应用版本（application version）**（当前 `1.0.0`），由 Go 核心与 TypeScript 适配层 bundle 共用。单一来源是 `internal/version`；`version` 子命令输出它，适配层在 `package.json` 中镜像它。发布构建可用 `-ldflags "-X .../internal/version.Version=X.Y.Z"` 覆盖。

- **协议版本跟随主版本。** `1.x.x` 实现协议 `v1`；协议发生 breaking change（协议 §11）时升为协议 `v2`，应用版本同步升到 `2.0.0`。核心与适配层必须同主版本、同协议。
- **SQL schema 版本是内部迁移计数器，绝不跟随发布。** 只在表结构变化时递增；打开数据库时强校验，不匹配则返回 `schema_mismatch` fail-closed，绝不静默迁移或重建数据。因此任何 `1.0.x` 的 bugfix 发布都不会让已有数据库失效。

版本号只是标签；兼容性来自真正被验证的机制：Go/TS 共享 request fixtures 锁死核心/适配层契约，`schema_version` 门禁锁死数据库，一切不匹配都以 fail-closed 拒绝而非静默修复。
